# Changelog

All notable changes to NauticPinnace are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
The version is defined once, in `src/Version.h`, and is what the device reports
to the NMEA 2000 bus - so a chartplotter's device list names the firmware that
is actually running.

Entries are marked with the boards they apply to. Unmarked entries apply to all
three.

## [1.3.0] - 2026-11-27

### Added

- Updates over NMEA 2000: firmware and web interface can be installed over the backbone with a CANable USB-CAN adapter and the Windows updater in `tools/N2kUpdate/` (or NauticPi), without WiFi or a USB cable. Every update has to be confirmed on the display's touchscreen - a dialog shows sender, content, versions, size and duration, and "Install (hold)" acts only after being held for 1.5 s; nothing on the bus or in the web interface can confirm, and 60 s without an answer declines (for the next 10 s that sender's offers get the same answer, so a sender stuck in a loop cannot keep the instruments covered). While the image streams in (compressed, at 30 % of the bus by default) a banner at the top of the instrument shows progress and remaining time, the instruments keep working, and a held "Cancel (hold)" stops it. The display checks the stream's CRC-32, reads the written image back and compares its SHA-256, checks that it was built for this board, and only then activates it, restarting after a 10 s countdown ("Restart now" / "Later"; paused while an alarm is active, and meanwhile only a strip under the alarm banner, so the anchor screen stays in view). The web interface that belongs to the release is approved in the same dialog and follows without a second one. New setting "N2K updates" on screen, "Accept updates over NMEA 2000" in the web interface (NMEA 2000 tab; config key `nmea2000.accept_updates`, default on, applies at once). Not possible in listen-only mode, on a display started in demo mode, or while an alarm is active; images from before this release (no firmware descriptor) are refused and still go over WiFi or USB. Protocol: `docs/N2K-UPDATE.md`; the display's side lives in `src/n2kupdate/`. The first firmware with the receiver has to be installed over WiFi or USB once.

- Every firmware image now carries a 64-byte descriptor at offset 0x120 (board, panel size, version) that both update paths check before anything is activated, and `tools/release_checks.py` checks before a release (it also prints the image id). Each env sets exactly one board flag (`BOARD_WAVESHARE_4` is new); a firmware build without one now fails instead of silently becoming a 4-inch image.

- Each display claims its NMEA 2000 address with a NAME of its own, derived from its MAC address (the model serial code carries the same number). Until now every display had the same NAME, so two of them switched on at the same moment could both keep address 42. Chartplotters list each display once more as a new device after this update.

- Bus-off recovery: a CAN controller that went bus-off - a short between CAN-H and CAN-L, for instance - is restarted by itself (after a repeat no more often than every 10 s) instead of staying silent until the display is restarted.

- The web interface can be replaced over WiFi on its own, without a restart and without touching the settings: tab Update, "Web interface (index.html.gz)". Release folders carry `index.html.gz` next to the firmware.

- AIS radar: north up or course up, set in the web interface (Display tab, AIS screen). Course up follows the course over ground, below 1 kn the heading, and an "N" marks north.

- **(Simulator)** `--n2kupdate-demo` plays an update over NMEA 2000 on screen (dialog, banner, countdown, notices; with `--shots DIR` it saves each state).

- Wind damping, adjustable in the web interface (Devices tab, next to the wind calibration), separately for apparent and true wind: four time constants - apparent wind speed (AWS), apparent wind direction (AWA), true wind speed (TWS), true wind direction (TWA and TWD) - in seconds, 0 to 30, default 2, 0 = off (config keys `cal.wind_damp_app_spd`, `cal.wind_damp_app_dir`, `cal.wind_damp_true_spd`, `cal.wind_damp_true_dir`). Apparent wind is for trimming and should react quickly; the true wind direction is for tactics - the shifts, not every gust - and takes much more damping; true wind speed lies in between, gusts should stay visible. True wind is computed from the undamped apparent wind and only then damped, so each setting acts on its own values only. After the time constant a sudden change in speed is 63 % through, and so is a small change in direction (a large swing in direction comes through faster). The filter allows for the actual spacing of the samples, so a sensor sending ten times a second and one sending once a second feel the same, and directions are averaged as directions - 359° to 1° passes through north instead of swinging round through south. A saved change applies at once, without a restart. The web interface takes the limits and the default from the firmware (`/api/info` gains `limits.wind_damp_s`).

- True wind direction from COG when no compass is sending - optional, off by default (Devices tab, "TWD fallback from COG" in the true-wind group of the wind damping; config key `cal.twd_cog`). Switched on, the course over ground (PGN 129026) stands in for a missing heading in TWD from 1 kn speed over ground, and once it does, it carries on until the speed drops below 0.8 kn - so a boat doing about 1 kn does not make the direction flicker between a value and "--"; a compass heading and another device's north-referenced true wind still come first, and TWS and TWA are not affected. Off by default because the course over ground is not where the bow points: current, leeway and drift put the direction a few degrees off.

- Autopilot mode from the bus: the Autopilot screen shows what the pilot computer itself reports - STANDBY, AUTO, WIND, NAV, NO DRIFT, or ACTIVE (engaged, mode not known) - and the setpoint that belongs to the mode (the held heading in AUTO, NAV and NO DRIFT, the held wind angle with its side in WIND, the newer of the two in ACTIVE). Read from the proprietary PGNs 65305, 65340 and 65341 of manufacturer code 1857 (payload starting exactly `41 9F`), and only from a device whose NAME (address claim, PGN 60928) says pilot computer (device class 40, function 150, manufacturer 1857); other manufacturers' frames and other devices are ignored. A report the rules cannot decide - two modes at once, or a bit they do not know - shows ACTIVE, never AUTO or another guessed mode. A new mode needs two identical reports in a row from the same address; with no status for more than 10 s the badge shows "--" instead of STANDBY. Until now the screen showed STANDBY whatever the pilot was doing, because the mode was never read from the bus. PGN 127237 keeps supplying heading-to-steer and rudder, never the mode; in STANDBY and without a setpoint from 65341 the screen shows its heading-to-steer as before. Read only - nothing is sent. The 65305 and 65341 rules follow the public description and are not yet confirmed on a real frame. The display remembers the pilot computer (NAME and address, in NVS) and finds it again after a restart without waiting for an address claim; one it has never seen deciding the mode stays "--" until it claims (see the README's new "Autopilot" section). New data source "Autopilot (pilot computer)" in the web interface (config key `sources.ap`); `/api/data` gains `apMode`, `apModeSrc`, `apSa`, `apStatus`, `apSetpoint`, `apSetpointKind`. Demo mode shows the pilot in AUTO on 215 degrees. PC simulator: `--ap-frames` checks every decoding rule on single frames and then plays synthetic example frames (built from the protocol description, not a bus recording) through the same decoder.

- Downwind sail selectable in the web interface, because not every boat carries a spinnaker or a gennaker (Display tab, screen list, Wind & Trim, "Downwind sail"): none, a spinnaker drawn in panels, a spinnaker drawn as a shaded balloon (the default) or a gennaker (config key `sail.spi_type`: `none`, `gores`, `balloon`, `gennaker`). It replaces the switch "Allow spinnaker": `sail.spinnaker` is still read when `spi_type` is missing or unknown (false = none, true = balloon) and is still written (true unless none), so an older firmware keeps showing or hiding the kite after a downgrade. The orange ellipse that stood in for the spinnaker is gone: the symmetric spinnaker is a crescent ahead of the bow with pole, guy and sheet, square across the bow on a run and turned to leeward on a broad reach, always clear of the mainsail and below the heading box; the gennaker is tacked at the tip of the stem, ahead of the jib's tack, with its clew to leeward and its sheet to the quarter, no pole. The spinnaker is shown as before (true wind angle over 100° below 25 kn, from 150° below 20 kn), the gennaker from 90° to 150° below 25 kn and from 150° to 160° below 20 kn - deeper than that it is blanketed by the main, and the normal running picture is drawn. Kite trim follows the apparent wind and is smoothed like boom and jib. On a dead run the rig no longer flips across the bow while the wind wobbles around 180°: beyond 175° the side it is on is kept. While a downwind sail is shown, the reef badge moves from above the bow into the cockpit, out of the kite's way. The compass card's letters (N, O/E, S, W) now lie above the boat, so no sail hides part of a letter any more; where a letter stands over the kite it gets a thin outline in the background colour, so it stays readable on the orange, also at night. The card's ticks stay under the boat, and the "Butterfly" label stays on top of the letters. Back on the Wind & Trim screen, or after a menu was open over it, the sails start from the current wind instead of swinging in from the last one.

- **(7B / 5B)** On-screen settings: a second QR code opens the web interface. While the display runs its own hotspot the two are numbered "1. Join the hotspot" and "2. Open the web interface"; in client mode the second one carries the address the display got in your network ("Web interface (same network)"). In landscape the two sit side by side in the right column - the hotspot QR code moves left to make room - and in portrait the new one sits below the first. Without an address (WiFi off, network not joined) there is no second code, and the hotspot code is labelled "Hotspot login".

- **(4")** On-screen settings: tap the QR code to switch it between joining the hotspot and the address of the web interface; the line above the hotspot button says which one is shown and what a tap brings. In client mode it starts with the address, since the hotspot is not running then. Nothing on the screen moves, and without an address the screen is the one it was.

- WiFi country code (web interface, tab WiFi). "Default (unchanged)" keeps what every display did so far: no country is set at all. A chosen country makes the display scan that country's channels actively - in Europe channels 12 and 13 too, which by default are only listened to - so a hidden network there is found and a network is found faster, and its hotspot announces that country. Takes effect with the restart after saving; `/api/info` shows the setting under `wifi.countryCfg` and what the WiFi reports under `wifi.country` (with policy `manual` that is the chosen country; with `auto`, the default, it can be the one the connected router announces). A rollback to an older firmware resets the country to Default.

- Watchdog on the main loop. Until now a display whose loop had hung stayed frozen until the power was cut: the firmware switches the interrupt watchdog off, and on the 7B and 5B with WiFi on the IDF task watchdog as well. The RTC watchdog is now fed from the main loop (at most every 100 ms, from one place): a pass that does not come back within 30 s resets the chip. Measured on all three boards, that reset is an RTC watchdog reset (rst 0x10) 30.0 to 30.3 s after the last feed, and it also boots a chip whose core 0 is stalled; the second stage, an RTC reset 2 s later, stays as a fallback and was never reached in the tests. Setup gets 120 s. While the NMEA 2000 task exists, the loop is only fed if that task's loop has moved within the last 30 s, so a task spinning on the other core is caught as well. On the 4" the IDF's own task watchdog still watches the web server's task and ends some hangs first - measured: a panic after about 5 s (reason 6) or a reset after about 15 s (rst 0x07) - and the boot log names it as a task-watchdog reset, not the loop watchdog's. On the 4" and the 5B the watchdog is off while a USB host is attached (ESP Web Tools does not switch it off, a browser flash would be cut after 30 s) and comes back 10 s after the host is gone. No setting. The boot log says what the last reset was (`[wdt] last reset: ...`): a reset of the watchdog's own is named by what it watched - the loop (with the part of the loop it stopped in, the screen and what core 0 did meanwhile), the NMEA 2000 task, setup or the update backstop - with the reset code it came back as, and on the 7B and 5B a panic handler that hung after setting the watchdog for itself is named as such; GET `/api/info` adds `reset` and `loopWatchdog` (state, the longest loop pass since boot, the count and the last reset of its own, from NVS `loopwd`), and the heartbeat line a `wdt=` field (the longest loop pass of its window). **(7B / 5B)** A crash late in a phase in which the watchdog is already counting - a slow start with the WiFi network out of range, the first minutes after an update, a stalled NMEA 2000 task holding the feeds back - keeps its backtrace and core dump: the panic handler sets the RTC watchdog to 10 s for itself without feeding the count that is already running, so that call is wrapped (`-Wl,--wrap=esp_panic_handler_enable_rtc_wdt`) to feed it first, and the build and the release tools refuse a 7B or 5B image without the wrapper. Test builds: `-DPANIC_PATH_TEST` adds the hang kinds loop, lvgl, block25, block35, irq0, irq1, both, lock, spin0, stall0 and rsthang to GET `/api/panic-test`, and lateabort (15 s without a feed, then `abort()`: the panic output and reason 4 are expected, not an immediate watchdog reset); `-DLOOP_WDT_OFF` never arms it, `-DLOOP_WDT_USB_OK` keeps it armed with a USB host (bench units flashed with esptool only).

### Changed

- **(Tooling)** `tools/release_checks.py` refuses firmware images built with `-DPANIC_PATH_TEST`, `-DLOOP_WDT_OFF`, `-DLOOP_WDT_USB_OK`, changed watchdog times (`-DLOOP_WDT_MS`, `-DSETUP_WDT_MS`, `-DRTC_STAGE_MS`, `-DUSB_REARM_MS`) or the tide bench flags `-DBSH_BENCH_POS` (every BSH request for 53.870 N 8.720 E, Cuxhaven) and `-DBSH_BENCH_EVERY_S=<s>` (a fetch every `<s>` seconds, 30 at the least, no retries); either bench flag adds a `[BSH] bench ...` line with the result, size, time and heap after every fetch (new check `testbuild`; each prints a fixed line at boot, which the check finds in the image).

- **(Tooling)** For the 7B and 5B, `tools/release_checks.py` refuses a firmware that still contains the hardware AES driver (new check `hwaes`), and the release scripts check, before they build anything, that the Arduino IDF libraries of the PlatformIO core they build these two boards in were compiled with every option of `custom_sdkconfig` in `platformio.ini`. pioarduino itself compares only a hash in the first line of `sdkconfig.defaults`, which every core building the project shares - so after the switch to software AES the release core would have kept its old libraries, hardware AES included, and shipped the broken tide download again.

- The interrupt watchdog (TG1) is switched off with a read-back now: the IDF's tick hook rewrites the same register every tick, and a write landing inside one of its read-modify-writes could be undone.

- Start-up no longer leaves the panel dark. The boot screen used to come up after a fixed 8 s wait and, with a WiFi network configured, only after the join as well - up to three attempts of 6 s - so a display whose network was not there stayed black for close to half a minute, which looked like a loose cable, a dead board or a hung firmware. The fixed wait is gone: the IO expander that switches the panel's power is asked until it answers and holds an output it is given (on the 5-inch board until it answers and takes its setting, see below), at most the old 8 s (serial log: `[boot] expander ready after N ms`), and on the 4-inch and the 5-inch board the USB console gets a short wait of its own (up to 1.5 s), only while a computer is attached. The radio is still started before anything is drawn, but the join now runs under the boot screen, which says what is going on: `Connecting to WiFi “Name” ... (attempt 2/3)`, then `Connected: http://<address>`, or why the network was not joined and what the display does instead (`WiFi “Name”: not found (201)`, `Internal hotspot “NauticPinnace…” active`, `http://192.168.4.1 – retrying in 30 s`; in German with the panel language set to German). The boot screen's status line and progress bar are drawn now - until now they were set but never rendered, the panel kept the last frame of the intro. With the medium font enlarged in the web interface, the status lines step down to the small font where they would otherwise run into the boat name. The serial log gains `[boot]` lines with the time of each step; about 10 s after start the expander is checked once more for whether it has kept its settings (`[boot] late expander check`), and a summary of the start-up follows - on the 4-inch and the 5-inch board as soon as a terminal is attached, because the lines of the first seconds are lost there when it is not. A touch controller whose configuration could not be read at start-up is no longer reprogrammed as if it had none (4-inch).

- The WiFi line of the on-screen settings shows the address with `http://` in front (`Hotspot mode active: http://192.168.4.1`), the form a browser needs - a bare address typed on a phone often ends up as a search.

- WiFi update (tab Update): `?target=fs`, which replaced the whole file system - stored settings included - and could not be undone, is gone; the web interface is installed on its own as `index.html.gz` instead (`?target=webui`; an old web interface's "filesystem" field now takes `index.html.gz` too and refuses a `littlefs.bin`). The firmware upload now goes through the same writer as an update over NMEA 2000: no 4 KB DRAM buffer, 4 KB erases instead of 64 KB blocks, and a firmware built for another board is refused after its first 352 bytes. While an update over NMEA 2000 runs, while a new firmware is being checked, or while a restart is pending, the upload answers 409, and so does `/api/restart` during an update or the check (a pending restart is allowed: it activates the update). On a board still running 1.1.0 or 1.2.0, install the firmware first and then, once its check is over ("Checking update" gone from the display) and the reloaded Update tab shows 1.3.0, `index.html.gz` in the old "Install filesystem" field - settings, polar table and boot logo stay; the old page's hint to install the filesystem first no longer applies (steps in `FLASHING.md` in the release package).

- A restart asked for in the settings during an update over NMEA 2000, or during the check of a new firmware, is postponed until it is over ("Restart after the update"); so is switching demo mode on. `/api/info` reports the update state: `otaState`, `verifySecondsLeft`, `runningSlot`, `runningImageId`, `lastInvalidVersion`, `rollbackCause`, `webUiId`, `webUiVersion`, `boardId` and an `n2kUpdate` block.

- The web interface is held in one of two PSRAM regions reserved at boot (about 0.2 MB more PSRAM on every board), so a new one can replace it without a restart; `/index.html` now gets the same page as `/` instead of the plain file from flash, which would be stale after such an update. The media screen's commands now reach the bus through the NMEA 2000 task instead of being sent from the display task.

- True wind is now computed on the display from the apparent wind, the only wind a boat actually measures (PGN 130306 reference 2), together with speed through water - speed over ground when there is no log - and the heading for TWD. A magnetic heading gets the deviation sent with it and the magnetic variation added. Until now the display showed whatever true wind another device on the bus sent, next to an apparent wind that had nothing to do with it; true wind from another device is now used only as a fallback on a bus without apparent wind, and then from the best reference still sending (water, then ground, then north) rather than from whichever message came last. Without boat speed, TWS and TWA show "--" while the apparent wind is still shown; without a heading, TWD does, unless another device sends a north-referenced true wind, whose direction then stands in, or the COG option above is switched on. The README's new "Wind" section has the rules.

- Demo mode now hands over only the apparent wind of its scenario and lets the display compute true wind, TWD and the wind history from it, like on a boat.

- Latitude and longitude in the data grids and the 7B/5B sidebar are shown as degrees and minutes (48°07.407'N, what chart plotters show) by default instead of decimal degrees. A display that still has the old default stored switches once with this update; a format chosen after that (web interface, Display tab, "Coordinate format") stays.

- The maritime icons of the OpenBridge Icon Pack are now the default icon set, on the panel and in the web interface; the Font Awesome glyphs stay selectable as "Classic" in the header of the web interface. A display that still has the old default stored switches once with this update; a set chosen after that stays. The licence notices now also name every OpenBridge icon without a `-google` suffix that is drawn on Google Material geometry - on the panel home, time, anchorwatch, trend, settings-iec, simulation and the four media icons, in the web interface clipboard, save-proposal, delete, image, palette-night and simulation.

- The Clock, Rudder and AIS screens draw faster and smoother. They now paint straight into their canvas instead of going through LVGL's per-call drawing, redraw only what changed (labels only when their text changes, a frame that would look the same is skipped), and the Rudder screen's canvas covers only the rows the gauge uses. Measured on the 7B, the slowest frame of the Clock screen went from 277 ms to 40 ms, the Rudder screen's from 70 ms to about 40 ms and the AIS screen's from 95 ms to about 33 ms, so touches and screen changes there no longer wait for a redraw. The shapes are now anti-aliased: the AIS range rings (centred exactly on the crosshair, same brightness as before) and the selection circle, the rudder band with its moving sector and the needle (now exactly on the axis), the day/night line on the world map and the tide curve. The Rudder screen's port and starboard letters beyond the ends of the band are gone - they lay outside the visible area on every board and never showed. On the AIS screen the outer range label moved inside the radar so it is no longer cut off. The Depth screen with its echogram, the wind history, the anchor watch, Wind & Trim and the attitude screen draw faster in the same way, without the speed-up changing a single pixel: they fill areas straight into the canvas, share one LVGL drawing context for runs of lines instead of setting one up per line, and the depth, wind history, anchor watch and Rudder screens skip a frame that would look the same. Measured on the 7B, the slowest frame of the Depth screen went from 157 ms to 70 ms, the wind history's from 93 ms to 66 ms and the attitude screen's from 154 ms to 132 ms; Wind & Trim (169 ms) and the anchor watch (45 ms) stay about where they were. The Rudder screen no longer clears the inside of its band, which the band paints over anyway. On the 7B and 5B a screen change normally redraws only the instrument area now, no longer the side rail and the sidebar with it.

- Numbers always take a decimal point, in the German interface as well: on the panel, in the web interface, in the Windows updater and in `n2kupd`, whatever language the display, the browser or Windows is set to. The number fields of the web interface (calibration on the Devices tab, the settings in the screen list, tank and battery rows) showed their values in the browser's format until now - "0,5" in a German browser - and now always show "0.5". A comma typed as the decimal mark is still accepted and read as a point, now in every browser: an English one used to make 5 of "0,5", and the polar table read "2,5" as 2. The arrow keys still step the values. The updater's bus share takes either mark too and rounds to a whole percent; `n2kupd --share` takes either mark, and a malformed number on its command line ends with an error message.

- AIS radar: target names show up to 15 characters, shortened with ".." to the room beside the target, instead of the first 7 ("DEMO VE"). Trailing blanks of a padded AIS name are dropped.

- Demo mode: the boat sails at about 92 % of the loaded polar, so Speed & Polar, Wind & Trim and VMG show a plausible performance. Against the example polar the old fixed speed curve gave 30 to 55 %.

- **(Simulator)** `--selftest` runs on simulator_7b and in every rotation: it reads the buttons' positions from the objects instead of clicking fixed places on the 4" layout. `--set nofix=1` takes away the own position while the rest of the demo runs on.

- **(Simulator)** `--demo-stop S` runs the demo data for S seconds and then stops it, so a bus going quiet can be watched on the PC: the values go blank one by one, then the "no data from the bus" strip comes up. With `--nodemo` the strip comes up 10 s after the start.

- **(Simulator)** The PC simulator loads `data/polar.json` like the device loads its polar, next to the configuration given with `--cfg`. Until now the Speed & Polar screen showed "--" for Polar and Perf there, and the README pictures with it.
- The online tide forecast (BSH) is fetched every 3 hours instead of every 30 minutes; a failed download is tried again after 2 and after another 10 minutes (at most twice per outage; new in this release, see Fixed). The BSH issues its forecast several times a day and every answer is the whole ~433 KB, about 20 MB a day near the coast. The request now names the boat's position rounded to 0.1 degree (about 11 km north-south, 6.5 km east-west) instead of to about 100 m; the nearest gauge is still chosen on the exact position, on the display. It identifies itself as `NauticPinnace/1.3.0 (+https://github.com/Ranman86/NauticPinnace)` instead of `ESP32HTTPClient`. The web interface (Devices tab, Tides) and the README's Security section now say what the download sends and where.
- The clock sync over WiFi takes the time server the router names in its DHCP lease (option 42), and uses `pool.ntp.org` / `de.pool.ntp.org` only when the router names none or that server has not answered with a set clock within 10 minutes; `time.nist.gov` is no longer asked. The serial log says which one is in use (`[BSH] SNTP: time server ... from the DHCP lease` or `[BSH] SNTP: pool.ntp.org (...)`). A clock the first sync attempt could not set now shows the time within seconds of the answer instead of at the next tide download.
- **(Release package)** `esptool.exe` is no longer part of the Windows release package. It bundles GPL-licensed flasher stubs, a Python runtime, OpenSSL and further libraries whose complete source would have had to ship with it. `flash.bat` now runs the `esptool.exe` 4.8.1 the user downloads from Espressif's release (`esptool-v4.8.1-win64.zip`), and checks its SHA-256 with `certutil` before every run; `FLASHING.md` says how, puts the web flasher first, and gains a Safety section (not a navigation device, not NMEA-certified, listen-only mode) and the NMEA 2000 trademark notice. The ZIP is about 9.7 MB instead of about 22.5 MB (1.2.0). The packages up to 1.2.0 still contain the exe.
- **(Web flasher)** The page loads ESP Web Tools at the exact version 10.5.2 instead of the newest 10.x, and says that it loads it from the unpkg.com CDN.

### Fixed

- The performance bar on the Speed & Polar screen was never drawn, on any board, since the first release: it was sized from its card before LVGL had laid the card out, so it was created 0 px wide. It shows now, green from 95 %, yellow from 80 %, red below.

- AIS radar: a name wider than its label box broke inside a word onto a second line ("NORDWI" / "N").

- AIS: class A vessels (commercial shipping) came in with speed and course swapped - the course, in radians, was taken as the speed and the speed as the course - so their vector on the radar pointed the wrong way and their CPA and TCPA were wrong. Class B was not affected. The second half of a class B vessel's static data (PGN 129810: callsign and ship type) is read now; it used to be dropped. The callsign labels a vessel whose name has not arrived yet and is shown next to the name in the info box.

- A display could crash and restart on its own, rarely, and more likely the more WiFi traffic there was: the check of the WiFi link every 15 s started a small task each time, and cleaning up after it could overflow the stack of the task doing that. The check now runs without a task of its own.

- A firmware update over a weak WiFi link broke off as soon as no data had arrived for 3 s. Once the file has started to arrive, it now waits 20 s. A phone or laptop that drops off the network in the middle of an upload does not hold the update that long, though: once it has sent nothing for 10 s, a new upload over WiFi takes over - the old one's writer is stopped before the new one starts, so two uploads never write at once, and should the old client come back, its upload is told that it was taken over (409 with gate `replaced`; "Cancelled: a newer upload over WiFi took over."). Within those 10 s a new upload gets 409 with gate `wifi` and the seconds left, and the web interface asks the display before it sends the file and says at once how long to wait, instead of sending the whole file for nothing. A second click on Install while an upload is running no longer starts a second one. `/api/info` gains `n2kUpdate.wifiTakeoverS`. A web interface upload less than 2 minutes after the last web interface install - the display keeps the old one's memory that long for pages still loading from it - is refused with its own text and the seconds left (409 with gate `grace`; "The web interface was replaced only a moment ago – try again in 97 s.").

- A network whose gateway does not answer pings - no router in the DHCP lease, or a firewall dropping them - made the display drop and rejoin the WiFi every 45 s, for good. The check now only counts against a gateway that has answered before.

- **(4")** About every second restart hung for a second and was ended by the hardware watchdog; it came back on its own, so nothing showed, but the boot log named a watchdog reset. The 4" now restarts the way the 7B and 5B do since this version (below).

- AIS radar: with more than 50 vessels on the bus, the table of 50 replaced whichever was heard longest ago, however close it was, so the vessels near you came and went. It now keeps the 50 nearest, a vessel on a closing course counting by how close it will come, and the count reads "11/50 targets" when only 11 of them are within the radar's range. Vessels heard only by their name no longer count. A vessel that gets a row now shows its name and callsign at once whenever they were heard before - while the table had no room for it, or before it was pushed out of the table or dropped from it (5 minutes without a position report, a bus dropout); until now it showed without them until its next static report, often minutes later. The display keeps name, callsign and ship type of up to 64 vessels without a row, ranked like the table, and the row takes them along. A vessel heard for the first time keeps its place among them until its first position report ranks it - for up to 5 minutes, enough for one at anchor that reports every 3 minutes - as long as fewer than half of the 64 wait like this; one whose position has not been heard for 5 minutes counts least, so boats that switch off near you do not hold the places for good. Measured in a simulation on the firmware's own code (4 hours of traffic within 30 to 480 nm, every vessel sending its static data every 6 minutes, 8 runs per case), of the vessels that got a row 98 to 100 % showed their name at once with up to 1,000 vessels reporting their position every 10 s, up to 640 every 30 s or 100 every 3 minutes, also with up to 100 boats switching off nearby (tried with 100 and 300 vessels reporting every 10 s); with 2,000 vessels every 10 s 95 to 98 %, with 200 every 3 minutes 91 to 94 % (without the cache: none). But not in every case: where many vessels report their position rarely, the waiting places run out - 75 to 79 % with 1,000 vessels every 30 s, 44 to 53 % with 2,000 every 30 s, and 34 to 48 % with 640 to 2,000 vessels that all report only every 3 minutes.

- AIS: a vessel that had lost its GPS and went on transmitting stayed on the radar at its old position; it now goes after 5 minutes like any other. A vessel just across the date line was never drawn and got a wrong CPA.

- AIS radar: without an own position the radar stayed empty while the count beside it went on showing the targets on the air, which looked like a fault. It now says "No own position".

- **(Web interface)** Tank and battery settings: a saved tank or bank the bus had not shown since the display started had no row in the Display tab's editor, so any save from that tab deleted its name, capacity and calibration - with the instruments still off, for instance. It now has a row marked "not seen", and emptying the row (for a battery, also setting System back to 12 V) is what deletes it. More entries than the display can keep (6 tanks, 4 banks) are refused with a message instead of the last ones being dropped in silence.

- Tank calibration: a field left empty was saved as 0 L, so with only some of the 25/50/75 % points filled in, the litres fell again as the tank filled. An empty field is now a point not measured, and a calibration whose litres do not rise with the level is refused with a message naming the tank. A tank with a calibration but no capacity now shows its litres on the panel, not only the percentage. A calibration at other points than 25/50/75 % (from an imported file) is no longer lost by a save.

- **(Web interface)** A tank's capacity reported on the bus now shows as a hint in the capacity field. It used to count as an entry, so any save from the Display tab fixed it as a setting and made a saved entry of every tank seen once, the four of demo mode included. A calibration typed without a capacity takes its 100 % point from it. A battery's system voltage is now saved on its own, without a name or a capacity.

- Tank and battery settings: a configuration file edited by hand and imported that listed a tank or a battery bank twice could lose data. The web interface showed one row for both, and its next save from the Display tab - whatever was changed there - dropped what only the other entry had: its name, capacity, 24 V or calibration. The tanks screen never showed a name that only the second entry had, and a duplicate took one of the 6 tank or 4 bank places, so a real tank or bank listed after it could be dropped. The entries are now merged when the file is read: the first one wins, and what it leaves empty - a name (one of only blanks counts as empty), a capacity, 24 V, or a calibration - comes from the other; a capacity and a calibration from different entries are combined only where they agree (the calibration's 100 % point is the capacity). The web interface applies the same rules to a configuration that still holds duplicates. Serial log, one line per list, with the number of repeated entries and the first repeat in the list: `[cfg] battcfg: 3 duplicate entries merged (first: bank 1)`.

- **(4")** Settings: the German "WLAN" label lay partly under its switch.

- A display that did not get into its WiFi network at start-up gave up after about 20 s and stayed in its own hotspot until it was restarted. On a boat that is the usual case rather than the exception: the display and a NauticPi hotspot get power at the same moment, and the Pi takes longer to start. The fallback hotspot now runs next to the station, and the network is tried again in the background - after 30 s, 60 s and from then on every 2 minutes - but only while no phone or laptop is connected to the display's hotspot, because looking for the network moves the hotspot's radio channel and would throw that client off. Once in, the display carries on exactly as if it had joined at start-up, and its own hotspot is switched off as soon as nobody is on it. Before falling back, the display looks for the network once and logs its channel, signal strength and security, or that it was not seen at all; the reason the WiFi driver gave for the last failed attempt is kept and shown - on the boot screen, in the settings' WiFi line (`WiFi: not found (201) – Fallback hotspot: http://192.168.4.1`, shortened where the line is too narrow; in station mode `Not connected: wrong password? (202)` while the link is being restored) and in `/api/info` (new `wifi` block: mode, fallback, `lastReason` with its name and age, `outageReason`, the scan made at start-up as `bootScan`, the next retry or `retryDeferred`, and the number of hotspot clients). Where the scan saw the network, the screens do not call it "not found" whatever the code says. Until now the reason was in the serial log only. A retry that is under way when a phone joins the display's hotspot is stopped at once, and if the network goes again while that phone is still on the hotspot, the display stays in the fallback rather than taking the hotspot down.

- **(7B)** NMEA 2000 could stay completely silent - no message received, no error counted, or the controller went bus-off after a while - although bus, cable and termination were fine. The board shares GPIO19/20 between its native USB socket and the CAN transceiver through a switch that the IO expander selects (EXIO5), and the expander's own firmware does not reliably keep that line driven: the switch fell back to USB, and the board even showed up as a USB device on a PC. The display now selects CAN the way that holds (mode register written again, the output written twice, then read back), checks it every few seconds and selects it again if it dropped; the serial log says `[exio] CAN selected` or `!!! CAN NOT selected`, and the periodic expander line gains `reads LOW - CAN cut off` when the switch is found on USB.

- **(5B)** The touchscreen did not react for the first seconds after every start, and for up to 10 s after the brightness was changed in the web interface or an update finished. The firmware took the board's IO expander for the chip on the 7-inch board, but it is a real CH422G, which has a protocol of its own: the commands meant for the other chip switched on the CH422G's display scan, which also drives the touch controller's reset line, until the next periodic read of the expander happened to switch it off. The expander is now addressed in its own protocol and only ever told to keep all its pins as inputs - the state the board spent most of its time in anyway - so the touch works from the start (serial log: `[disp] CH422G ready: scan off, IO0..7 inputs`). The brightness setting has no effect on this board, as before: the expander can only make all eight pins outputs at once, and two of them are the isolated inputs DI0/DI1. The serial log's I2C scan lists every address that answers; it used to stop after 18.

- A firmware update over WiFi reported "Update failed" after about a minute, although it had worked and the display was already running the new firmware. The device restarted before its reply had left (the web server sends a reply only after the request has been handled), so the page never heard back; the Restart button's reply was lost the same way. The restart now comes about a second after the reply, and the page shows the success and waits for the display to come back. This takes effect from the next update on: the old firmware is the one that answers, so updating a 1.1.0 or 1.2.0 board to this release still ends in "Update failed" (`FLASHING.md` in the release package has the steps).

- The Clock screen's world map showed day and night the wrong way round from late September to mid March: night where the sun was up, and the day/night line as vertical steps instead of a curve. The day/night boundary is now correct all year, and the sun's position on the map now allows for the equation of time and uses an accurate declination, so the map, the sun dot and the sunrise and sunset times agree (the sun and the line were up to about 4 degrees of longitude off before).

- The online tide forecast (BSH) failed on the 7B and 5B with "IncompleteInput" or "NoMemory": the reply was read as finished whenever the data paused for a moment, and once it arrived whole, the parse needed more PSRAM than the secure connection left free. The reply is now read until it really ends (15 s without data counts as a failure), and the stations are parsed one at a time with only the nearest usable one kept, which cuts the parser's memory from about 14 KB to 3.4 KB on every board with the same result. A failed download is tried again after 2 and after 10 minutes instead of only at the next regular download; the serial log says how much arrived, how long it took and how much memory the parse needed.

- **(7B / 5B)** The online tide forecast (BSH) still broke off on most downloads - on the 5B about three times in four, on the 7B nearly two times in three - with `esp-aes: Failed to allocate memory` in the serial log, followed by `IncompleteInput` (or `HTTP -5`). The secure connection keeps the incoming data in PSRAM, where the chip's AES unit cannot write directly, so for every piece of the 430 KB reply (8 KB each, about 50 per download) it borrowed small buffers of internal RAM (about 1.6 KB, and a few bytes more) - the same RAM the WiFi receive buffers come from - and whenever one was not to be had, the download was lost. AES now runs in software on these two boards (`CONFIG_MBEDTLS_HARDWARE_AES=n` in `platformio.ini`): it decrypts in place and borrows no internal RAM per piece (the connection's own state grows by about 250 bytes, once), for about half a second (7B) to one second (5B) more per download. Measured with 24 downloads per board before and after: the 5B used to lose 7 of 8 downloads right after a start, now none. The 4-inch was never affected. The rebuild of the IDF layer that this takes also brought the LittleFS component from 1.22.3 to 1.23.3 (`THIRD-PARTY-NOTICES.md`).

- **(7B / 5B)** In the on-screen settings, the WiFi status line no longer touches the network name field below it.

- After a change between summer and winter time, the local time on the Clock and Anchor screens could be an hour off for up to a day: the offset from the internet time sync was only taken at the sync itself, about once a day. It now follows the Central European rule all the time, so the change shows within about a second. A local offset sent on NMEA 2000 (PGN 129033) still takes precedence over it. Switching demo mode off no longer throws away the time from the internet sync either: until now the Clock screen then showed no time until a GPS time came, and that showed as UTC until the next sync, and demo mode switched on again showed its sample date instead of today.

- Rollback after an update now actually works. The bootloaders of all three boards always had it, but Arduino's startup code confirmed every freshly installed image before `setup()` even ran, so a firmware that crashed or hung after an update stayed installed and only USB could repair it. Now a new image is confirmed only after it has run properly for at least a minute - setup finished, the loop, the display and the NMEA 2000 task alive, and for an update over NMEA 2000 the updater heard again - and the display returns to the previous firmware by itself within about three minutes otherwise, backed by the RTC watchdog against a complete hang (300 s, never fed; its reset also boots a chip whose core 0 a panic handler has stalled), which hands over to the loop watchdog once the image is confirmed. Three crashes in a row in the first 30 minutes of a new firmware switch back as well - but only to the image it replaced: an update that was written into the other slot and then abandoned has its first sector erased, so nothing can ever start it. The previous firmware then says once what happened (crashed, power lost during the check, no reception, ...). The comments and texts that claimed the opposite (`main.cpp`, the web interface's Update tab, `partitions_16MB.csv`) are corrected. The restart of a rollback after a failed check skips the shutdown steps (switching the WiFi off and the like) and resets the chip directly, the way a crash ends.

- The anchor-drag alarm banner stays visible while a menu is open (settings, home launcher, licences, language); until now only the buzzer sounded there. Touches go through it to the menu below.

- Wind values no longer freeze when the wind sensor stops sending: after 10 seconds without a wind message every wind value shows "--", and the next message starts the display afresh.

- No value freezes any more when its sender stops: position, speed, course, heading, depth, rudder, attitude, rate of turn, heave and waves, engine, the autopilot's heading-to-steer and rudder, and the route each go to "--" after 10 seconds without a valid reading; air and water temperature, humidity, pressure, the distance log, tanks, batteries and the stereo after 30 seconds; the magnetic variation after 10 minutes. Until now every value stayed on the last reading for good, like the wind (above) - an engine that had been switched off kept showing 2000 rpm, a finished route stayed "active". A sender that keeps talking but marks a value "not available" no longer keeps the old one alive: a GPS that has lost its fix used to keep the last position looking current, to the anchor watch too. AIS targets are dropped after 5 minutes without a position report on every screen, no longer only while the AIS radar is showing, and a target's CPA goes blank with the own position instead of keeping the last one.

- When the bus delivers no data at all for 10 seconds, an amber strip at the top of the instrument says "NO DATA FROM NMEA 2000 BUS" with the time since the last value, and every bus value is blanked at once - on the screens, in the 7B/5B sidebar, the data grid and the web interface. Address claims, heartbeats, the anchor sync of other displays, updates over NMEA 2000, the system time and the stereo do not count as data, so a bus kept busy by other displays with every instrument switched off is reported too. The strip goes by itself with the next value; it does not blink, lets touches through, and is not an alarm (no buzzer, and updates over NMEA 2000 stay possible). With the anchor watch armed and no current position, it turns red and says "ANCHOR WATCH: NO FIX" - the drag alarm used to go quiet without a word when the position was lost. And a drag alarm that is already sounding now stays up when the position goes - showing "-- m" - until a fix inside the circle comes back or the watch is switched off; it used to clear, buzzer included, exactly then. The clock, the internet tide forecast and the histories stay. `/api/data` gains `bus` and `busQuietS`. The tide forecast and the automatic day/night theme now use the last known position, so they keep working while the GPS is quiet.

- Screens that drew missing values as real ones: Wind & Trim drew a missing rudder angle as a blade amidships, the attitude screen a level horizon without roll and pitch, the VMG screen reported missing data as "Low wind", and the AIS info box kept the values of the moment it was tapped, after the target was long gone.

- **(Web interface)** The Live tab no longer keeps the last values when the display stops answering: they go to "--" and the badge says offline. It shows the bus warning as well. A tank or battery bank whose values have gone blank stays in the Display tab's editors, so a save there keeps its name and settings.

- After demo mode is switched off on a display that started on the bus, the messages queued while the demo ran are discarded instead of being shown as current.

- **(7B / 5B)** After a screen change the demo banner no longer covers the anchor alarm banner.

- The wind-history page now holds six minutes of valid true wind regardless of how fast the wind sensor sends: it takes one sample per second while TWD and TWS are known. It took one per wind message before, so with three wind messages every 100 ms - what a bench simulator sends - its 360 samples covered about 13 seconds.

- With no true wind angle known, the Wind & Trim instrument showed "0° Stb" for TWA, named the point of sail "Head to wind" and drew the flow lines from dead ahead; it now shows "--" and leaves the angle-dependent parts out. The sails follow the apparent wind then, with flapping and running judged by apparent-wind limits, and stand neutral when no wind is known at all.

- A wind message whose speed or angle the sender marks as not available no longer turns into a nonsense value on the display.

- Restarting a display - from the web interface or the on-screen settings, after an update, or after a crash - no longer floods NMEA 2000 with error frames. The restart left the CAN controller running and connected to the bus while the chip switched back to its slower start-up clock, so for a moment it listened and answered at half the bit rate and put an error frame on traffic it misread. A device sending at that moment could be driven off the bus; on a test bench whose only data source is a USB-CAN adapter, every display then lost every value. Measured on the 5B and the 4-inch: about 300 bus errors per restart. The controller's transmit line is now held idle before every restart.

- **(7B / 5B)** A restart - from the web interface or the on-screen settings, or after an update - no longer hangs for two seconds and comes back through a watchdog reset. The restart now uses the chip's system reset, the one the start-up code and the brownout handler use, instead of a CPU reset that could stall while switching the cache off.

- **(7B / 5B)** A firmware only a little larger than this one would have left the panel dark: on these boards the program itself runs from PSRAM, in 64 KB pages, and the frame buffer was the last thing to get its 1.2 MB. One page more - measured with a build about 10 KB larger - and the panel got no memory, the start-up never finished, and after an update the display rolled back after 90 s. The frame buffer's place is now held before the screens' drawing memory takes its share, and when PSRAM runs short it is the drawing memory that gives way: the panel lights up and the display stays reachable and updatable, and only the screens built last lose their drawing area (serial log: `[Arena] !!! PSRAM SHORT`; tested on the 7B with 256 KB held back: the clock's world map stayed empty, every other screen worked). The drawing memory also no longer takes more than it asks for - the heap used to round it up by 35 KB - and it asks for what the screens really use plus a margin: measured on the 7B with every screen visited, it was 55 KB larger than needed. That PSRAM is now free for the running firmware, which needs it (the web interface's settings document lives there on these boards); the build check counts on 64 KB staying free. With this release the 7B and the 5B both use every 64 KB page of program code that still leaves the drawing memory its full size (`tools/psram_budget.py`: about 20 KB to spare, no further page). `/api/info` gains a `psram` block (`arena`, `arenaWanted`, `arenaUsed`, `free`).

- **(Tooling)** After every 7B and 5B build, `tools/psram_budget.py` reads the firmware's PSRAM needs from `firmware.elf` and prints how many 64 KB pages of program code are still left before the drawing memory would have to shrink (`[psram]` lines in the build output; also runs on its own: `python tools/psram_budget.py <build dir>/firmware.elf`). The release tools refuse a 7B or 5B image that would not leave the full drawing memory, and one without the watchdog's panic wrap (above), which also fails the build.

- **(Tooling)** The serial heartbeat calls its bus error count `buserr` instead of `busoff`: it has always counted error frames, not bus-off episodes, which the driver logs on lines of their own.

- **(5B)** With a computer on the USB socket that does not read the serial console - a terminal closed with the cable left in, or a PC without one open - the display froze for about two seconds: the USB driver waits that long for a host that is still connected but takes nothing, and measured on the bench it did so in the heartbeat after the test tool had closed the port. A console write now gives up after at most 0.1 s, and right after the next heartbeat line - or the first line of the start-up summary 10 s after start - the console stops waiting for that host altogether until a terminal reads again: such a host now costs the display about 0.1 s, once. The start-up summary is then printed again for the next terminal that reads. A terminal that reads still gets the whole log, and the last lines before a restart keep the full 0.1 s to get out; only a host that reads very slowly - more than 5 ms for a few hundred bytes - could now lose a line. The start-up and the 4" and 7B consoles are unchanged.

- **(Tooling)** The serial start-up log no longer shows two error lines that were never a fault: `E (837) task_wdt: delete_entry(240): task not found` (7B and 5B; on the 7B cut off after a few characters, e.g. `E (85`) and `disableCore1WDT(): Failed to remove Core 1 IDLE task from WDT` (all three boards). The start-up took two tasks off the task watchdog that were never on it; it now asks first. What the task watchdog watches is unchanged. On the 7B the last line of the early log is no longer cut off either: starting the console threw away what was still being sent.

- Wind & Trim and the attitude screen: the rudder angle under the rose was written in white straight onto the gauge - next to unreadable on the light track of the light theme, and the amidships tick ran through it in every theme. It now sits on a small box in the colours of the heading box at the top, with a green (starboard) or red (port) border, since the box covers the first few degrees of the fill.

- Wind & Trim and the attitude screen: a long value in a top corner - "4° Stern", "13° Stb", "10.5 kn" - ran into the 330 or 030 label of the rose below it. Where the widest value of a field would not fit beside the label, its side or unit is now set smaller, on the number's baseline - decided per field from that widest value, so the layout stays the same while the number changes.

- Engine screen: a four-digit value in one of the cards ran into its unit ("2676hPa" for the oil pressure). It now moves left as far as it needs to keep clear of the unit, but never past the card's edge, and takes a smaller font only where even that is not enough.

- **(7B / 5B)** Wind history: the "W" of the compass letters was cut off at the left edge of the rose, and the single letters stood beside their spokes rather than on them; they are centred on their spokes now.

- **(Tooling)** esptool's `image_info` now shows the firmware's own version and the name "NauticPinnace" from IDF's app description at image offset 0x20, and the ELF a core dump is read against carries the same strings. It held whatever the framework's precompiled libraries were built with: "esp-idf: v4.4.7 38eeba213a" and "arduino-lib-builder" on the 4-inch, and on the 7B and 5B `git describe` of the working tree at the time their IDF libraries were compiled and the first word of the project folder's name. ### Added

- Latitude and longitude can now be shown in degrees and minutes (48°07.407'N, what a chart plotter writes) or in degrees, minutes and seconds (48°07'24.4"N) instead of decimal degrees - a new "Coordinate format" setting on the Display tab, which applies to the two coordinate fields wherever they appear in a data grid or in the sidebar. A field's decimals then count for the last part, minutes or seconds. Default stays decimal, so an existing configuration looks exactly as before. Asked for in GitHub issue #3.

- The Wind & Trim instrument can show the last minute of wind speed as a curve running from the centre of the rose out to the wind pointer - the strip chart of a wind plot laid along the pointer, newest sample at the rose, older ones migrating inward, wind strength across. Four settings in the sail section of the web interface: off, true wind only, apparent wind only, both. Off by default.

- Trial: the maritime icons of the OpenBridge Icon Pack (CC BY 4.0) as an alternative to the built-in Font Awesome glyphs - the same icon for the same meaning as NauticPi (anchor, wind, depth, engine, the media controls, the alarm triangle ...), on the panel and in the web configuration. The icons are rasterised at build time into small LVGL fonts by `tools/gen_icons.py` from the mapping shared with NauticPi. Everything belonging to the trial, and how to remove it again, is listed in `ICONS-TRIAL.md`.

- The anchor watch now keeps in step with NauticPi over the NMEA 2000 bus. Setting, lifting, moving, arming or clearing the anchor alarm on either device has it the same way on the other about a second later, in both directions, over the proprietary PGN 131035 (manufacturer 2046, fast packet). Both sides decide who wins from the message alone: newer revision wins, and on the same second the lower node number - so a device whose clock lags still carries its own change through. The state is broadcast on every local change plus a ten-second heartbeat, which is what brings a device that was just switched on into agreement. An adopted state re-evaluates the drag alarm at once rather than waiting for the next cycle.

- The anchor screen gained a "lift anchor" action - the set button turns into it while an anchor is down - and shows the time the anchor fell. Until now an anchor could be set but never cleared.

- The BSH tide download (every 30 minutes) can be switched off in the web interface (Devices tab); the tide screen then falls back to the tide data on the NMEA 2000 bus, if a sender offers any. Time synchronisation over WiFi is unaffected by the switch.

- After a restart the device returns to the instrument that was showing when it was switched off, instead of always starting on the first one. Configuration and licence screens are excluded: they never count as "the last screen".

- **(Tooling)** The release package now carries all three boards instead of the 4-inch alone: one ZIP with a folder per board (`4/`, `7b/`, `5b/`, each with its flash images, the merged full-flash image and a manifest) and the flashing tool, licences and instructions once at the top. `flash.bat` and `flash.sh` take the board as their first argument (`flash.bat 7b COM5`) or list the three and ask - the wrong firmware leaves the screen dark without warning, so they never guess. FLASHING.md covers the 7B's USB driver and a fallback for the 5B should a transfer stall.

### Changed

- The media screen (formerly named after the stereo's brand) is now called "Media" ("Medien" in German), on its tile, in its title and in the documentation; the brand name no longer appears in the project's sources and documentation. It controls the stereo exactly as before - only the project's own naming changed. Saved configurations are unaffected, since screens are stored by number; the screen type the web API reports is now `media`.

### Fixed

- The WiFi hotspot's name as printed on the configuration screen, as encoded in the QR code and as broadcast by the radio could differ from one another: the MAC address the name is derived from was read into an uninitialised buffer whenever the network interface was not yet up, and each of the three read it at a different moment. All three now derive the name from the chip's permanent MAC.

- In demo mode the wind-history sampler stopped recording five seconds after boot, because the demo data never refreshed the wind timestamp. (Wind trace only; no released screen was affected.)

- With demo mode off and no stereo on the bus (or in listen-only mode), tapping next or previous on the media screen filled in a title and artist from the demo playlist, and play/pause and the mute buttons changed their icons for a stereo nobody had heard. The demo playlist now runs only while the demo does; without a stereo the controls leave the screen as it is. Switching demo mode off at runtime on a device that booted on the bus now also clears the demo values, as it already did on a device that booted in demo mode.

- The licence notices now cover everything the firmware links, read again from the linker maps of all three boards: `LICENSES/` gains the BSD-3-Clause texts of lwIP, wpa_supplicant, littlefs and the TLSF memory allocator, one MIT text carrying the copyright lines of FreeRTOS, the Xtensa HAL, esp_littlefs, cJSON and the code LVGL bundles, and the newlib C-library notices. FreeRTOS is now credited under its actual licence (MIT, Amazon) instead of Apache-2.0, the binary-only WiFi and PHY libraries under Apache-2.0 instead of an unnamed Espressif licence, and the font notices no longer claim a reserved font name that Montserrat's licence does not declare. The browser flasher page links the notices and licence texts next to its install buttons.

- The source code of the LGPL libraries in exactly the versions each board links - the Arduino-ESP32 core (2.0.17 on the 4-inch, 3.3.11 on the 7B and 5B), AsyncTCP and ESPAsyncWebServer - is now attached to every GitHub release as `src-*.zip`, and THIRD-PARTY-NOTICES.md names the exact upstream tags and commits and the build directory each board's object files land in for relinking.

- The licence screen on the device now names what that board actually links: its own core and library versions, the full copyright lines of the two web-server libraries (four holders and LGPL-3.0-or-later on the 7B and 5B), the ESP-IDF components underneath, and LovyanGFX on the 4-inch only. It says where the full texts are (THIRD-PARTY-NOTICES.md and LICENSES/ in the GitHub repository), and the OpenBridge icons are credited under a heading of their own instead of under the fonts.

- The flashing instructions and the README no longer say that a freshly flashed device starts in demo mode: out of the box it reads the NMEA 2000 bus, as it has since v1.1.0, and the demo can be switched on in the web configuration.

- The firmware-only USB update in the release package's FLASHING.md now writes `boot_app0.bin` along with the firmware. On a board that had been updated over WiFi, the command given until now wrote the new firmware into the app slot the board was no longer starting from, so the old firmware kept running as if nothing had happened. The instructions also name the web interface's Update tab as the route without a cable, and that a firmware-only update keeps the web interface already on the board.

- **(Tooling)** The `esptool.exe` in the Windows release package now comes with the notices and licence texts of everything bundled inside it - Python runtime, OpenSSL, libffi, bzip2, xz, zlib, pyserial, intelhex, the PyInstaller bootloader and the Microsoft runtime - in `esptool-4.8.1/notices/`, and with the source of pyserial and intelhex next to the esptool source.

- **(Tooling)** The release tools refuse stale or unsuitable images instead of packaging them: an image that carries paths from the build machine's user profile or leftover old names, a `data/` folder holding credentials, or a build older than the sources stops the run - for the release package and the web flasher alike, on all three boards. `platformio.ini` now pins every library to the exact version the notices name.

## [1.1.0] - 2026-08-27

Two more displays, and a great deal of work behind the picture.

NauticPinnace now runs on the 7-inch Waveshare ESP32-S3-Touch-LCD-7B and the
5-inch -5B alongside the original 4-inch board. All three share one source tree
and one user interface; the two 1024x600 boards additionally carry a navigation
rail, a configurable data sidebar and a full-screen launcher. The screen picture
can be rotated in 90-degree steps on every board, sensors can be calibrated and
duplicate data sources pinned from the web interface, and firmware can be
updated over WiFi.

Nothing here changes the stored configuration format: a config file from v1.0.0
is read unchanged, which is why this is a minor release despite its size. The
one migration is automatic - see the note on CAN pins under Changed.

### Added

- NauticPinnace now runs on two more displays - the 7-inch Waveshare ESP32-S3-Touch-LCD-7B and the 5-inch -5B, both 1024x600 - which share the identical user interface down to the last line of code and differ only in their pin map, console wiring and panel timings; each has its own build environment (waveshare_esp32s3_7b, waveshare_esp32s3_5b) and board definition.

- The screen picture can now be rotated by 0, 90, 180 or 270 degrees (Display tab in the web interface, the device restarts itself to apply it), so the unit can be mounted on its side or upside down - touch and swipe navigation turn with it.

- Eleven sensor calibrations can now be entered in the new "Devices" tab of the web interface (depth offset, wind-vane rotation and wind-speed factor, compass offset, log factor, roll, pitch and rudder zero points plus a mirrored rudder sense, water-temperature and pressure offsets); the correction is applied once as the value arrives from the bus, so every screen shows the corrected reading from the next message without a restart, and the defaults are neutral, leaving an uncalibrated device exactly as before.

- Data sources can now be pinned per category - position, compass, wind, depth, speed through water, environment and attitude - so on a boat with two GPS receivers or two compasses the display no longer just follows whichever device transmitted last: the new Devices tab lists every sender seen on the bus with its source address, message count and age, and "Auto" keeps accepting any sender.

- Firmware and filesystem can now be updated over WiFi from a new "Update" tab - no USB cable: the page names the version currently installed, shows an upload progress bar, and waits for the device to come back while it reboots itself. A firmware file that is not an ESP32 image is rejected before anything is written, and the page warns to install the filesystem before the firmware and to do updates at the dock rather than at sea.

- Tap the ring of the compass card in the centre of the Wind & Trim instrument (and of the Attitude screen that shares it) to switch the card between course-up, as before, and north-up, where a marker on the rim shows the current heading; the choice is saved and survives a restart, and only the card turns - the relative-wind ring, the boat and the wind pointers stay bow-up.

- The CAN TX/RX pins set in the web interface are now actually applied, so the firmware also runs on rewired or third-party boards - until now the bus always opened on the compile-time board pins no matter what was configured. A pin pair that cannot work is rejected in favour of the board defaults, and the boot log names the pins the bus really opened with, because a wrong pin does not announce itself: the controller comes up and simply never receives a frame.

- After an over-the-air update the boot log names the slot the firmware is actually running from, which is the only way to tell a successful update from a silent fall-back to the previous image, since both slots carry the same firmware; the image also marks itself healthy only once the panel, the configuration and all screens are up. Note that the shipped prebuilt bootloader does no automatic rollback: a truncated or corrupt upload simply never boots and the previous version is kept, but a complete image that crashes at runtime still needs a USB cable.

- CPU load and free memory can be picked as data fields like any NMEA value, so device health fits in a data-grid cell, on the engine page, or - on the 7B and 5B - in a sidebar cell.

- **(7B / 5B)** Support for the 1024x600 panels of the 7B and 5B boards: they are driven directly through the ESP-IDF RGB panel interface, because the LovyanGFX driver the 4-inch uses never produced a usable picture on them. Both run their pixel clock at 36 MHz instead of the vendor's setting (30 MHz on the 7B, 21 MHz on the 5B), whose refresh rate flickers visibly, and the panel is fed from small DMA buffers, which stops the horizontal smearing that appeared as soon as the app drew into the same memory the panel scans out of.

- **(7B / 5B)** On the 1024x600 boards the instruments are drawn natively at 1.25x the 4-inch design - bigger fonts and real geometry rather than an upscaled 480-pixel picture - inside a 600x600 square that keeps its size in portrait as well as landscape, with the demo and anchor-alarm banners now spanning that instrument column instead of the whole screen width.

- **(7B / 5B)** On the 1024x600 boards the rail's home button opens a full-screen launcher showing every active screen as a labelled tile with a large icon, plus a settings tile - tap a tile to jump straight to that screen, and close the launcher with the X in the corner or a swipe up. The grid sizes itself to the number of tiles, up to 24 of them without scrolling, and a caption too long for its tile drops to a smaller font instead of being broken mid-word.

- **(7B / 5B)** The 1024x600 boards gain permanent chrome around the instrument: an 88 px navigation rail carrying the NauticPinnace brand mark and Home / Previous / Next / Settings, with Previous and Next given the largest touch targets, plus a 336 px sidebar of up to eight configurable value cells. The cells use the same fields as the data-grid screens (label, unit, decimals) and pick up a change made in the web interface immediately, without a restart.

- **(7B / 5B)** Mounted in portrait, the 1024x600 boards rearrange their permanent chrome instead of merely turning the picture: the navigation rail becomes a 600 x 88 bar across the top, the data sidebar becomes a band along the bottom whose value cells reflow into a grid of up to four columns instead of one tall stack, Previous and Next stay the largest buttons (1.5x the width of Home and Settings), and the instrument keeps its full 600 x 600 square in either orientation.

- **(7B / 5B)** With the display rotated to portrait, the menus and the boot screen lay themselves out for the taller screen instead of running off its edge: the settings page stacks the hotspot block and its QR code under the WLAN column, the launcher drops to a three-column grid centred vertically, the language picker spreads its buttons over the extra height, the licence page keeps its accept button on screen (on first boot that button is the only way past it), and the boot screen's logo and progress groups move toward the centre instead of drifting to opposite edges.

- **(7B / 5B)** The permanent data sidebar is now configured under Display in the web interface: 1 to 8 value cells, each with field, label, unit and decimals, preset to SOG, depth, apparent wind speed, heading and battery voltage - and because the setting is stored on every board, a configuration file stays portable between the 4-inch and the large displays.

- **(7B / 5B)** The repository now carries a panel bring-up sketch with its own build environment for each of the two new boards (bringup_7b, bringup_5b): it drives the RGB panel directly, without the rest of the firmware in the way, and steps the pixel clock upwards while printing the refresh rate and the panel's PSRAM read rate for each step - the measurement that settled the 36 MHz the firmware now ships with.

- **(Tooling)** The deploy tool now identifies the serial port by its USB identity and always says which port it chose and why: the 7-inch board's CH343 bridge is unmistakable, while the 4-inch and the 5-inch report the same USB ID, so with both attached it lists the candidates and asks instead of guessing - and the port, whether detected or pinned with -Port COMx, is now used by every flashing step, including both halves of a full deploy.

- **(Simulator)** The PC simulator now has a 1024x600 variant (simulator_7b) that runs the real nav rail, sidebar and home launcher, and any simulator build can produce its own documentation set: `--shots DIR` walks every configured screen plus the home, settings and licence overlays and writes one image each, named after the screen title and skipping unconfigured grid slots, while `--settle MS` sets the render time per shot and `--home` opens the launcher directly; captured images leave out the demo banner and the fps overlay. The repository carries the resulting set from the 1024x600 build - 126 images covering every screen plus the launcher and the settings page, each in light, dark and night and in both landscape and portrait.

- **(Simulator)** The PC simulator now honours the configured screen rotation and shows exactly what a rotated panel shows - the window keeps the panel's shape and the picture lies on its side inside it - with clicks and swipes following the rotated layout, including the rule that a swipe must start on the instrument rather than on the nav rail or the value sidebar.

- **(Tooling)** Serial render diagnostics on the 1024x600 boards: the five-second heartbeat now reports the instrument's own canvas paint separately from the rest of the display work and adds the worst display refresh of that window with how much of it went into getting the pixels to the panel, and about once a minute one line lists every screen visited since boot with its slowest paint - which is how the slow screens in this release were found. The PC simulator additionally logs every PSRAM arena allocation, which is how the arena on the device is sized.

### Changed

- The wind instrument repaints markedly faster on every board: its filled discs, zone rings and sail shapes are now painted straight into the instrument image instead of being handed to LVGL one scanline at a time, which on the 5B alone accounted for 198 ms of a 261 ms repaint.

- The 4-inch board keeps building against exactly the core v1.0.0 was released and tested with, even though the two 1024x600 boards need a newer one (Arduino 3.3.11 / ESP-IDF 5.5.5, required for the RGB panel's bounce buffers) that used to overwrite it during installation.

- AIS targets on the radar now change colour at the CPA/TCPA alarm limits set in the web interface - yellow at twice those limits, red at them - so the radar warns at the same distance as the alarm instead of at fixed thresholds.

- Existing devices keep their NMEA 2000 bus after the update: the CAN pins now come from the board definition unless a pin is set explicitly for modified hardware, and a stored configuration still carrying one of the two historical pin pairs is treated as "not configured" instead of being taken at face value.

- Out of the box the device now starts with live bus data instead of the demo simulation, and it comes up in the firmware's own dark and light themes - the factory configuration no longer freezes an older black-and-blue palette over them.

- The web configuration page is now served pre-compressed, cutting it from about 130 KB to under 40 KB on the wire - a load that took 4.4 s on the 7-inch and 13.4 s on the 5-inch drops to roughly a quarter of that - and a device whose filesystem does not carry the compressed copy is still served the plain page as before.

- About 10.8 KB of internal RAM is given back on every board: the AIS target table and the wind, depth, speed, heave and pressure history rings now live in PSRAM, leaving more of the memory that WiFi, the web server and the online tide forecast were running out of.

- A panic can now be read back from flash instead of dying with "Elf write init failed" on every crash: the 16 MB layout gains a core-dump partition, paid for with 64 KB from each of the two app slots, which stay equally sized so an over-the-air image can never outgrow the inactive slot - the LittleFS partition keeps its offset and size, so settings, the web UI and the polar table survive the update.

- The README now covers all three boards side by side - panel, touch controller, CAN pins, console wiring and the extras the 5-inch adds - and gains a step-by-step guide to reaching the web configuration: hotspot or joining an existing boat network, which one to pick and why, and the promise that you cannot lock yourself out, because after three failed connection attempts the display falls back to its own hotspot, so a wrong password costs one boot rather than a serial cable. The new Devices tab (sensor calibration and N2K source selection) and the screen-orientation setting are documented, and the AIS note is corrected: target colouring follows the CPA/TCPA thresholds from the configuration.

- **(4-inch)** The 4-inch release package can still be built now that each board keeps its own toolchain directory: the packaging script takes the boot image and the flashing tool from the 4-inch board's own copy.

- **(7B / 5B)** On the 1024x600 boards every instrument page is now laid out for the larger panel instead of staying at its 480 px design size - the wind rose and its corner readouts, the anchor watch and its button band, the AIS radar, the depth echogram, the rudder arc, the autopilot compass, the battery and tank cards, the route/VMG/weather tiles, the media controls and the data grid all fill the screen, with correspondingly larger type and touch targets.

- **(7B / 5B)** Themes saved in the web interface now scale with the panel, so one stored theme produces the same design on the 1024x600 boards as on the 4-inch instead of leaving small text on a large screen.

- **(7B / 5B)** On the 1024x600 boards menu transitions and the scrolling licence text now move smoothly instead of stepping five times a second, while the screen refresh itself is deliberately held back so the web interface keeps answering while the display is busy.

- **(7B / 5B)** The settings, licence and language screens now fill the whole panel instead of a 600 x 600 square in one corner - the licence text box gets the extra height, so much more of the text is visible before scrolling, and the language buttons become larger targets.

- **(7B / 5B)** On the 1024x600 boards the settings screen uses the extra width: WLAN, display theme and the language/licence row fill the left column, the hotspot block with a larger auto-connect QR code (176 px instead of 112 px) sits on the right, and the on-screen keyboard spans the whole panel width at 280 px tall, so the keys are finger-sized. Controls that the larger fonts had outgrown get honest room as well - the WLAN label no longer sits under its own switch, the licences button no longer clips its caption at both ends, and the listen-only switch gets a row of its own.

- **(7B / 5B)** On the 1024x600 boards the clock page carries a larger world map generated at its own 600x250 resolution instead of reusing the 4-inch one, so coastlines stay fine rather than coarse, with the clock, date, sun/moon lines and tide curve moved down to match.

- **(Tooling)** Before offering any action, the deploy tool now asks which board or simulator you are targeting and keeps that choice on screen, instead of silently sending every build and flash to the environment named in platformio.ini - the released 4-inch product. Non-interactively use `deploy.bat <action> <board> [COMport]` or `-Board 4|7b|5b|sim|sim7b` (names such as 7inch or 5b are accepted); only `deploy.bat simulator` still defaults on its own, to the 480x480 simulator, because it flashes nothing.

- **(Simulator)** The PC simulator now runs on the same PSRAM budget as the board it stands in for - 3.35 MB for the 4-inch, 4.42 MB for the 1024x600 boards, instead of a flat 4 MB - so a screen that asks for too much memory fails at the desk rather than on the boat.

### Fixed

- Screens carrying a lot of text are far more responsive - scrolling the licence page went from roughly 1 to 6 frames per second on the 5B - because text is no longer re-measured several times per drawing pass for a scrollbar that could never appear.

- While a full-screen menu is open - settings, licences, the language picker and the new home launcher - the instrument behind it is no longer drawn at all instead of being fully repainted under the opaque menu, so menu scrolling and buttons respond immediately: on the 5B one frame of licence scrolling had been spending 1,160 of its 1,190 ms rendering an instrument nobody could see (all boards; the home launcher itself exists only on the 7B and 5B).

- The web interface no longer goes unreachable while the device still shows a healthy WiFi connection: the link is now checked end to end with a gateway ping every 15 seconds and rebuilt after three unanswered probes, radio power saving is forced off (with it on, large page loads stalled to nothing), and the station runs in 802.11b/g, which stopped the connection from wedging every one to two minutes while a browser was talking to it.

- Tide heights are now referenced to chart datum instead of gauge zero: the gauge's datum correction silently came out as zero at every station, so every predicted height was published far too high (302 cm at Cuxhaven).

- Turning demo mode off in the web interface no longer crashes the device, and no longer leaves a unit that had booted in demo mode with nothing reading the bus - every value blank, which looked exactly like broken hardware or a dead cable. It now restarts itself with a notice on the display.

- Overlapping saves - a save the browser re-sent, or a save and a configuration import at the same time - could silently produce a configuration parsed from a mixture of two request bodies; each request now buffers its own body, and one that is too large or cannot be buffered is answered with an error instead of being parsed (the same applies to importing a configuration and to uploading a polar table).

- An interrupted boot-logo upload no longer leaves the web interface wedged until the next restart, and two uploads arriving at once no longer corrupt each other.

- The tide forecast now picks the nearest gauge that actually carries data: stations that report no chart datum or no tide events (Meldorf, Neuwerk) used to win purely on distance and hide a complete gauge a few kilometres away. Predicted events are also kept strictly ascending in time, so the clock screen's "next tide" really is the next one; heights more than 30 m from chart datum are discarded as implausible, and a genuine reading of 0 cm (water standing exactly at gauge zero) is no longer mistaken for a missing value.

- The web interface header now shows the address the page was actually loaded from instead of always displaying the hotspot address 192.168.4.1, which was wrong whenever the device was joined to a boat network.

- A tide gauge whose name ends in a cut-off special character can no longer put stray characters into the station name on the clock screen, because transliterating it no longer reads past the end of the text.

- **(7B / 5B)** On the 1024x600 boards the settings page no longer comes up with parts of it missing - an empty screen list, the wrong IP address - which happened whenever the device ran out of memory while assembling its configuration or spliced two replies into one connection.

- **(7B / 5B)** The online tide forecast now works on the 1024x600 boards: the 433 KB reply from the BSH service used to be parsed in the small internal RAM that the secure connection and the WiFi receive buffers need at the same moment, so the download stalled and a request that had already been answered failed as incomplete - sometimes taking the device down with it; the parser's memory and the fetch task's 12 KB stack now sit in PSRAM (the 4-inch keeps its proven path unchanged).

- **(7B / 5B)** On the 1024x600 boards the picture no longer drifts out of alignment while the device writes to flash or serves the web UI: the panel interrupt now keeps running when the flash cache stalls, and the driver recovers from an underrun instead of restarting the whole frame.

- **(7B / 5B)** On the 1024x600 boards WiFi is configured for a configuration UI rather than for throughput - frame aggregation off, smaller receive and transmit queues, and the network buffers kept out of the PSRAM the panel already saturates - so the web interface keeps answering a browser's parallel requests instead of falling silent while the display still reports a connection, and TLS is given PSRAM as well, so the online tide forecast's secure connection no longer fails for lack of memory.

- **(7B / 5B)** Changing screens and opening the home launcher on the 1024x600 boards redraw far faster: a full-screen repaint used to cost 0.8-0.9 s, almost all of it work repeated once per drawing pass - scrollbar, border and rounded-corner handling on full-bleed background containers that need none of it - and the number of passes a full repaint takes has been halved from 120 to 60.

- **(7B / 5B)** On the 1024x600 boards the WiFi credentials now survive a filesystem update: they are kept in a second area that the update does not overwrite and are restored on the next boot, instead of the device dropping off the network until the WLAN was retyped on the touchscreen.

- **(7B / 5B)** On the 1024x600 boards the serial console is no longer flooded with watchdog errors - several hundred lines a second at startup and around a hundred a second in operation, which held up the rest of the boot - because the watchdog is now switched off in a single step, a step that on the newer core could otherwise abort into a boot loop.

- **(7B / 5B)** On the 1024x600 boards, opening a full-screen menu could reboot the device because the drawing needed a working buffer mid-frame and the memory pool was by then too fragmented to hand one out; those buffers are now reserved at startup while the pool is still intact.

- **(7B / 5B)** On the 1024x600 boards the NOW marker on the depth echogram and the diagonal points of the wind rose (NW, SW) no longer wrap onto a second line, where the larger fonts had outgrown label boxes that were only scaled proportionally.

- **(Tooling)** Building for one board no longer breaks the next: the 4-inch environment now has its own package and build directory and the simulator its own build directory, so a 4-inch or simulator build no longer silently wipes the 7B and 5B firmware (the build still reported success and the next flash found nothing) and no longer evicts the toolchain the panel boards need. Build output also moved out of the project tree, whose path contains a space that the 1024x600 builds refuse.

- **(Tooling)** The deploy tool can now be driven from a script or a build step: `deploy.bat -h`, `--help` and `/?` reach the help instead of aborting with a parameter error, an unknown action prints the usage and exits with code 2, and an unattended run no longer hangs on a "press any key" prompt or swallows a failed build - the exit code is returned first.

- **(Tooling)** On Windows the build no longer falls back to a full recompile after ccache was installed with winget: it is now also found in the winget install location, so a shell that still carries the old PATH keeps using the compiler cache.
